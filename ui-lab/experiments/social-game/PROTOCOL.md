# 実験の境界とログ

## 開始前

共通入力のハッシュ検証、ブラウザ接続、配信、空の出力先を確認する。モデル名/推論/速度指定、実際に観測できた設定、ツール/CLI版、開始コミット、プロンプト全文とハッシュを記録する。起動を自動化する場合はrun-id・作業先・セッションID・モデルの対応を照合し、取り違えたセッションへ修正指示を送らない。

接続失敗なら試行は「環境不成立」で止める。実装後にブラウザ不可が分かった試行は、検証済み試行の速度・品質順位へ混ぜない。今セッションの接続成功を次セッションの成功扱いにしない。

## 測定

運営側の準備と本体の制作を分離する。各プロセスの開始/終了UTC、実行時間、待機時間、親の設計/レビュー/統合時間、子の実装/修正時間を分ける。並列実行の経過時間は各時間の合計ではない。

初回完了の定義は「実装担当が成果物と自己検証結果を提出した時点」。この時点のフォルダーを運営側で変更不能なアーカイブまたはGitコミットとして保存する。独立レビュー前にスクリーンショットも同じ寸法で保存。修正後成果物とは別に識別し、後から初回を上書きしない。

各CLI呼出しのusageを原記録と一緒に保存し、同じ累積値の重複加算を避ける。input、cached input、output、reasoning outputを別表示し、内数を加算しない。キャッシュ以外の入力はinput−cachedで計算可能だが「新しい資料の量」そのものではない。実費は確認できる請求情報がある場合だけ記録する。取得不能/中断はnullと理由を残す。

親と子を合計した総使用量と、各担当の内訳を両方表示する。親の会話が試行をまたぐ場合は区間境界と差分方法を記録する。Fast要求と実配信tier確認を区別する。

## 役割と再試行

次のユーザープロンプトで役割を決める。単騎は自ら実装/自己検証/修正し、運営から途中の助言を受けない。ハイブリッドは途中レビューの時点・回数・予算を開始前に決める。独立評価者は両方式を同じ受入れ表で採点する。レビューが増えたら追加分を隠さず記録する。

最初は各条件1回の動作確認でもよいが、優劣の結論には同条件の反復が必要。反復時も前の実装を読ませない。シードデータ・素材・要件が変わった試行は別条件。完全に同じ画像が再生成されることより、合格率・見た目の評価・総負荷のばらつきを見る。

## 成果物

各案：index.html、DESIGN.md、RETROSPECTIVE.md、TEST-REPORT.md、実装ファイル。運営：run.json（隣のRUN-TEMPLATE.jsonを複製）、実プロンプト、段階別usage、初回/最終のスナップショット、スクリーンショット、受入れ表。生ログはローカル保管、公開用は秘密や個人情報を含まない集計と証拠のみ。

この準備タスクは実験の開始・モデル起動・公開サイト実装を行わない。次セッションはREADMEから復帰し、ユーザーのテストプロンプトを待つ。
